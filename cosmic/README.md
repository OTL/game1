# コズミック・イーター

小さな岩のかけらから始まり、あらゆる天体を喰らって成長し、最終的に**ブラックホール**になったらクリアの、
2D 宇宙成長（育成×サバイバー）ゲームです。

## 遊び方

- **移動**：マウスドラッグ（またはタッチ）でプレイヤー天体を動かします。画面中央から指・カーソルを離した方向へ慣性を伴って進みます。
- **捕食**：自分より小さい天体にぶつかると、相手を破壊して質量（経験値）を吸収できます。破片は自動でこちらに引き寄せられます。
- **被弾**：自分より大きな天体にぶつかるとダメージを受けます。HP が 0 になると、直前の進化段階の始まりまで戻ってやり直しになります（強化はその段階の開始時点まで巻き戻ります）。
- **レベルアップ**：質量が一定量に達するたびに、3 枚のカードから強化を 1 つ選べます。
- **進化**：質量のしきい値に到達すると次の姿へ進化します。

  岩石片 → 小惑星 → 準惑星 → 惑星 → 巨大ガス惑星 → 褐色矮星 → 恒星 → 巨星 → 中性子星 → **ブラックホール（クリア）**

- **捕獲（惑星以上で解放）**：進化段階が「惑星」以上になると、自分よりずっと小さい敵（質量が自分の
  35%以下）をロックオンして捕獲し、周回する衛星にできます。PC は **Q キー**、スマホは画面右下の
  🛰ボタンで捕獲します。同時に保有できる数は進化段階に応じて増加します（惑星/巨大ガス惑星:1 →
  褐色矮星:2 → 恒星:3 → 巨星:4 → 中性子星:5 → ブラックホール:6）。捕獲した衛星は自機を公転しながら
  触れた敵にダメージを与え、近くの破片（小天体）を自動で引き寄せて質量獲得を手伝いますが、
  自分よりずっと強い敵に触れられ続けると破壊されてしまうこともあります。保有数は左上のHUD
  （🛰 x/y）に表示されます。既存の「衛星」アップグレードは汎用の小型衛星として引き続き機能し、
  捕獲システムとは独立に共存します（どちらも同じ公転・接触ダメージの仕組みを共有）。
- **ゲームモード**：タイトル画面で選べます。
  - **通常モード**：クリアまで約 60 分を狙ったペース配分（序盤の進化は数分、終盤2段階＝巨星・
    中性子星はそれぞれ約 9〜10 分）。
  - **加速モード（お試し）**：通常モードと全く同じ段階別ペース配分を、比率を保ったまま一律
    約 1/12.7 に短縮した、短時間（5〜6 分程度）で最後まで試したいプレイヤー向けのモード。
  
  モードはセーブデータに保存され、「つづきから」では選んだモードのまま再開されます。
- **エンドレスモード**：ブラックホールに到達してクリアした後、リザルト画面の「そのまま遊ぶ
  （エンドレス）」を選ぶと、ブラックホールのままプレイを継続できます。詳細は本README末尾の
  「第3回」セクションを参照してください。
- **セーブ**：数秒ごと・進化やレベルアップなどの節目に自動で保存されます（ブラウザの localStorage）。タイトル画面の「つづきから」で再開できます。
  ※本アップデートでバランス・セーブ形式を変更したため（`cosmic-eater-save-v4`）、以前のセーブデータは
  引き継がれず「はじめから」扱いになります。

## 強化（アップグレード）の例

溶岩惑星・惑星環・希少鉱脈・重力場強化・硬質地殻・衛星・磁場収束・オーロラ帯・推進機関・地殻再生・
核融合暴走（クリティカル）・密度増加・彗星の尾・隕石シールド・加速衝突・質量転換効率・重力感知・磁気嵐など、
20 種類以上。恒星以降でのみ解放される「太陽フレア」「コロナ質量放出」「重力波」「伴星」「不死の芯」といった
上位の強化もあります。同じ強化を重ねて選ぶとレベルが上がり効果が強化されます。

## 実機フィードバック対応（終盤の破綻・画質・ペーシング）

実機（スマートフォン）でのプレイフィードバックにより、終盤（恒星 Lv13、プレイ時間 03:53）で
画面全体が巨大でボケた敵テクスチャに埋め尽くされ、MISS・ダメージ数値がスパムし、廃止したはずの
点線軌道円も残っているという破綻状態が報告された。原因分析と対応は以下の通り。

### 1. 終盤の「敵が画面を埋め尽くす」問題の原因
「分裂」ではなく **敵同士の合体（`updateEnemyMutualGravityAndCollisions`）の無制限な連鎖** が
主因だった。敵同士が近づくと大きい方が小さい方を吸収して質量が増えるが、この吸収質量に上限が
無かったため、プレイが長引くほど1体がどんどん肥大化し、`massToRadius`（質量の立方根）で半径も
際限なく育っていた。加えて敵のスポーン数上限（旧: 26体）や画面内密度の制御が緩く、遠くのスポーン
も含めて狭い範囲に敵が密集しやすかった。対応:
- 敵1体の質量に `BALANCE.enemyMassCapMult`（プレイヤー質量の4倍）の上限を導入。合体・スポーンの
  どちらでもこれを超えない。上限に達した合体は超過分を破片として放出する（吸収側の得は残す）。
- ワールド全体の敵・破片の総数に上限（`maxEnemies`=20, `maxFragments`=40, `maxTotalBodies`=55）を
  設け、超過分はプレイヤーから最も遠いものから間引く（`pruneBodyCounts`）。
- プレイヤー近傍の敵密度にも上限（`nearViewSoftCap`）を設け、密集している間は新規スポーンを控える。
- 質量比の大きい「脅威」個体は、外周寄りの遠い位置にのみスポーンするようにし、プレイヤーより
  大幅に大きい敵がいきなり近接して視界を覆うことを防いだ（質量上限と合わせて、脅威敵の見た目
  サイズはプレイヤーの 4^(1/3)≒1.6 倍までに収まる）。
- 破片（吸収可能な質量粒）はそもそも敵化しない設計のままであることを確認・維持（分裂の連鎖が
  発生しない）。

### 2. 巨大な敵がモザイク状にボケる問題の原因
固定の低解像度テクスチャキャッシュ（近似描画: 最大64px角、フル品質: 最大220px角、球面テクスチャの
元絵も200×100px固定）を、画面上の実表示サイズまで拡大描画していたことが原因。加えて
devicePixelRatio（Retina等で最大2倍）が解像度計算に反映されていなかった。対応（LOD: Level of Detail）:
- `Renderer.drawRotatingGlobe` で、天体の画面上の実表示ピクセル数（半径×2×devicePixelRatio）に
  応じてキャッシュするテクスチャの解像度を動的に決定するように変更（近似描画の上限を160px角、
  フル品質の上限を480px角に拡大）。
- 球面投影の元になる正距円筒図法テクスチャ（equirectangular）の解像度も、必要な表示サイズに応じて
  4段階（140×70 〜 680×340）で再生成するようにし、大きく見える天体ほどクレーターなどのディテールが
  つぶれず見えるようにした。
- `ctx.imageSmoothingEnabled`/`imageSmoothingQuality` を明示的に高品質設定にした。
- `node cosmic/tools/simulate-pacing.js` とは別に、Playwright で実際に終盤相当の巨大天体を画面いっぱいに
  表示して確認済み（後述の検証結果を参照）。

### 3. 点線軌道円の完全削除
`Renderer.drawLockonMarker`（ロックオン対象の周りに薄くパルスする点線の輪を描く関数）自体を
削除し、呼び出し箇所も削除した。ロックオン情報は左上のHUDパネル（`#lockon`）のみで表示する。
ワールド空間に円やガイド線を描く処理はコード上どこにも存在しないことを確認済み。

### 4. MISS・ダメージ数値のスパム対策
被弾・ダメージ処理は毎フレーム正しく計算しつつ、**表示だけ** を対象ごと（敵の uid・プレイヤーの
被ダメージ・プレイヤーの質量獲得）に集計し、`BALANCE.floatFlushInterval`（0.35秒）ごとに合算して
1回だけ浮遊テキストを出すように変更（`queueFloat`/`flushFloatAggregates`）。シールドのMISS表示も
`BALANCE.missFlushInterval`（0.5秒）のクールダウンを設け、接触し続けても毎フレーム表示されないようにした。

### 5. 彗星の尾アップグレードの視覚的な軌跡
移動軌跡に接触ダメージ判定を持つアップグレードは「彗星の尾」（`tail`、`pulseDamage` を
`playerRadius*1.5` の範囲で自機位置に適用）と特定した。これまで対応する見た目が存在しなかったため、
自機の直近の移動履歴（`player.tailTrail`）をフェードする発光プラズマの帯として描画する
`Renderer.drawTail` を追加。帯の太さはダメージ判定半径（`playerRadius*1.5`）と連動させ、見た目と
判定範囲が一致するようにした。

### 6. ペーシング調整（通常モード ≈60分 / 加速モード）
`cosmic/tools/simulate-pacing.js`（Node.js 上で質量獲得を確率的に近似シミュレーションするツール）を
新規作成し、実機フィードバックの実測値「03:53で恒星(Lv13)到達」から接触試行レートを逆算した上で、
進化段階ごとの質量獲得倍率（`NORMAL_STAGE_PACING_MULT`）を調整した。結果:

```
$ node cosmic/tools/simulate-pacing.js
=== 加速モード（お試し）(massGainMultiplier=1.0 固定) ===
  平均クリア時間: 5.3 分   （恒星到達: 3.93分 ≈ 実測の 03:53 と整合）
=== 通常モード（段階別倍率） ===
  平均クリア時間: 59.9 分
    小惑星: 2.78分  準惑星: 6.28分  惑星: 10.81分  巨大ガス惑星: 16.55分
    褐色矮星: 23.05分  恒星: 30.92分  巨星: 40.65分  中性子星: 50.64分
    ブラックホール: 59.92分
```
序盤（岩石片〜準惑星）は数分間隔、終盤（巨星以降）は8〜10分間隔になっており、要求どおりの
ペース配分になっている。この段階別倍率は `creditMass`（質量獲得を行う唯一の関数）内で
一律に適用されるため、キル・破片吸収・パッシブ回収などすべての質量獲得源に一貫して効く。
加えて、ブラウザ内での実機相当の動作確認として、`window` に一時的なデバッグフック
（時間加速・内部state参照・任意ステージへのジャンプ）を追加した実機検証も行った上で、
コミット前にそれらのデバッグコードは削除している。

## 見た目・演出（リアルな宇宙表現）

### 1. 単一光源の一貫したライティング
ワールド全体で共有する「遠方の恒星」を1つだけ定義しており（`WORLD_LIGHT`、超低速にしか角度が
変化しない実質固定方向）、プレイヤーを含む全天体・全パーティクルが常にこの同じ方向から照らされます。
球体（準惑星以上）はテクスチャ側でこの方向のライティング・縁の減光（limb darkening）を焼き込み、
自転しても明暗境界（ターミネーター）は常にワールド座標で同じ向きを保ちます。小さい／不規則な天体は
「形状（アルベド、方向性の光は焼かない）」と「固定シェーディングマスク」を分離して合成することで、
タンブリングしていても同じ光源方向を維持しています。夜側は完全な黒ではなく、背景光でわずかに
見える程度の明るさ（ambient floor）を残しています。彗星の尾・浮遊する塵・破片のハイライトも
すべて同じ `WORLD_LIGHT` を参照するため、画面内のどの天体も矛盾のない「同じ太陽の下」に見えます。

### 2. 小さい天体は球にしない
岩石片〜小惑星クラス（小惑星・彗星核・敵対天体、およびプレイヤーの序盤2段階「岩石片」「小惑星」）は、
円形テクスチャを不規則な輪郭（複数の調和振動を重ねた半径関数）でクリップした「ジャガイモ型」で
描画し、非等速の角速度ゆらぎ（タンブリング）で回転させています。準惑星以上（自己重力で丸くなった
天体：準惑星・惑星・ガス惑星・褐色矮星・恒星・巨星・中性子星・ブラックホール）だけが球体＋自転に
なり、プレイヤーも準惑星へ進化した瞬間にジャガイモ型から球体へ切り替わります。

### 3. ケプラー運動の徹底（静止天体ゼロ）
真空中なので敵天体・破片の速度に減衰摩擦は入れていません。小惑星帯は各々ばらばらな初速のまま
漂流し続け、彗星は視界を高速で横切ります。プレイヤーの質量に応じた簡易重力（`applyPlayerGravity`）
が近傍の天体に働き、質量が大きいほど通過する小天体の軌道が目に見えて曲がります（スイングバイ的
挙動）。敵天体同士も近傍限定の簡易相互重力で緩やかに引き合い（`updateEnemyMutualGravityAndCollisions`）、
接近しすぎると衝突して大きい方が小さい方を飲み込み、破片を放出します。天体数の上限が決まっている
ため、これらはすべて O(n²) の総当たりで計算しても 60fps を維持できます。

### 4. 衝突の運動量保存
敵を撃破したときや敵同士が衝突したときに生成される破片は、親天体の速度をそのまま引き継いだ上に
爆発による放射状の速度を加えます（運動量保存）。破片は個々に回転しながら、以後は減速せず真空を
漂います。

### 5. 彗星の尾は反太陽方向
彗星の尾は進行方向の逆ではなく、恒星（`WORLD_LIGHT`）の反対方向へ伸びます。まっすぐ青い
イオンの尾と、進行方向側へやや曲がる白いダストの尾の2本を描画しています。

### 6. 画のトーン・雰囲気
- 背景に天の川のような微光の帯を1本、ごく薄い視差でドリフト表示しています。
- 漂う微細な塵パーティクルを3層のパララックスで常時流しており、各粒はゆっくり自転していて
  `WORLD_LIGHT` との内積で明るさが変わります（光を受けて煌めくように見えます）。
- プレイヤー（カメラ）が速く動いているときは、進行方向と逆に塵がわずかに尾を引き、スピード感を
  演出します。
- ブルーム風のグローは恒星・巨星・褐色矮星・中性子星・ブラックホールの降着円盤など発光体のみに
  限定しています。
- 薄いビネットは毎フレームの canvas 再描画コストを避けるため、常時表示の CSS オーバーレイ
  （`#vignette`）として重ねています。
- ロックオン対象の表示はワールド空間の円やガイド線を一切描かず、左上のHUDパネル（`#lockon`）
  のみで行っています（実機フィードバックにより、パルスする破線の輪も含めて完全に廃止しました）。

### 天体の球体描画（準惑星以上）
横方向にシームレスな正距円筒図法（equirectangular）テクスチャをオフスクリーンで生成し、縦スライス
ごとに球面へ投影して描画しています。端に近づくほどテクスチャが圧縮される球面マッピング、
`WORLD_LIGHT` 方向のシェーディング、縁の減光、惑星以降は薄い大気の縁光も再現しています。
ガス惑星・褐色矮星・巨星は縞模様が、恒星・中性子星は表面の輝きが自転とともにゆっくり流れて見えます。
パフォーマンスのため、画面上である程度大きく見える天体のみこのフル品質描画を行い、それ以外の
小さい・不規則な天体（ジャガイモ型）は自転位相を離散化した「フレーム」単位で（形状＋固定シェーディング
マスクを合成した）描画結果をキャッシュし、drawImage 1回で済ませることで、多数の天体が同時に映っても
描画コストを抑えています。

### 多層パララックス背景
星空を3層（うち2層は星の瞬き付き）でパララックス表示し、カメラの移動に応じて視差スクロールします。
星雲は星空とは別レイヤーとしてオフスクリーン生成し、ごくゆっくりドリフトしながら明滅（アルファ
ゆらぎ）します。ときおり流れ星も出現します。進化段階が進むにつれ、背景の色調も序盤の暗青から
恒星帯の暖色、終盤の深い紫へと連続的に変化します（彩度は抑えめ、暗部を締めたトーン）。

## 実機フィードバック対応（第2回：終盤の敵サイズ・アップグレードの整合性・実プレイ調整）

### 1. 敵サイズ分布の再設計（根本原因の修正）

**症状**: 前回対応（`enemyMassCapMult=4`）後も終盤で敵が自分より常に大きく、画面を圧迫する。

**根本原因の特定**: 敵の表示半径が `massToRadius(mass) = 6 * mass^(1/3)`（質量の単純な立方根）で
計算されていたのに対し、プレイヤー自身の表示半径は `STAGES` の `radiusBase` テーブルを使った
別の補間式（`playerRadius()`）で計算されていた。序盤の小さい質量では両者はほぼ一致して見えるが、
終盤の質量（数百万〜一千万超）では `massToRadius` が実質破綻し、同じ質量でも敵の方がプレイヤーより
何倍も大きく描画されてしまっていた（例: 質量1300万の場合、`massToRadius` ではワールド半径1400を
超えるが、プレイヤー側の `radiusBase` は最大でも80程度に収まるよう意図的に設計されている）。
これが「敵は常に自分よりデカく見える」体感の直接の原因だった。

**対応**:
- 敵の表示半径を新設の `enemyVisualRadius(mass)`（`entities.js`）に置き換えた。中身は
  `playerRadius()` と全く同じ「`STAGES.radiusBase` を使ったステージ内補間」で、同じ質量なら
  プレイヤーと敵が同じ見た目の大きさになることを保証する。
- 敵1体の**質量**（戦闘力）の上限を `enemyMassCapMult` で `4倍 → 2倍` に引き下げた。
- サイズ**分布**を目標分布（大半は自分より小さい餌、2割前後が同格〜やや大きい、明確に大きい
  脅威は同時1〜2体まで）に基づいて再設計した（`BALANCE.prey/even/threatMassMultRange` と
  `preyChance`/`evenChance`、`data.js`）。
  - 餌（質量倍率 0.15〜0.65）: 76%
  - 拮抗（同格〜やや大きい、0.7〜1.3）: 19%
  - 脅威（明確に大きい、1.4〜2.0）: 5%
- 敵のスポーン基準質量は、実際のプレイヤー質量ではなく `state.enemyScaleMass`
  （log空間で平滑化した緩やかな追従値）を基準にロールするようにし、敵スケールが
  プレイヤー質量に「遅れて追いつく」ようにした。死亡・リスポーン時は即座にリセットする。
- プレイヤー近傍に同時に存在できる「脅威」（質量比 `BALANCE.threatRatioThreshold`=1.3 以上）の
  数を `BALANCE.maxThreatsNear`（2体）で制限し、上限に達している間の新規スポーンは強制的に
  非脅威にロールし直す。
- 画面短辺の40%を超える表示半径にはしない安全弁（`screenRadiusCapFor()`）を、スポーン時・
  敵同士の合体成長後の両方に適用した。質量（戦闘力）と表示半径を分離してクランプすることで、
  「戦闘バランス」と「見た目の上限」を独立に安全に制御できるようにした。
- 敵同士の**合体の頻度**も抑えた。合体した個体には `mergeCooldown`（4.5秒）を設け、
  クールダウン中は合体させず反発（めり込み解消）だけ行うことで、同じ個体が連鎖的に
  肥大化し続けることを防いだ。

**実測結果**（Playwright + Chromiumで自動プレイし、進化段階ごとに集計。詳細は本セクション末尾）:
通常モード・加速モードの両方で、プレイヤー近傍の敵の質量比分布はおおむね目標どおり
（餌74〜100%・拮抗0〜15%・脅威0〜15%、同時脅威数は最大2〜3体）に収まり、近傍の敵の画面占有率は
全ステージを通して最大でも約20%（40%の安全弁は未到達）に収まることを確認した。

### 2. アップグレード説明文と実挙動の突き合わせ

`data.js` の全アップグレードについて、説明文が指すメカニクスが実装と一致しているか1件ずつ
確認した。特に「高速移動」関連の疑いから着手したが、調査の結果、**最も重大な不整合は
「核融合暴走」（会心）と「重力感知」の2つ**だった。

| ID | 名称 | 問題 | 対応 |
|---|---|---|---|
| `critical` | 核融合暴走 | 説明文は「%の確率でダメージが2.2倍」だが、実装は確率要素が一切なく、常に `1 + val%*1.2` を掛けるだけの別物の効果だった（2.2倍という数値もコード上どこにも存在しなかった）。 | 説明文どおりの確率発動クリティカル（`rng()`で判定、成功時ダメージ×2.2）に実装し直した。発動時は「会心!」の浮遊テキストを表示し体感できるようにした。 |
| `sense` | 重力感知 | 説明文は「索敵と警戒の範囲が拡大する」だが、実装は敵AIの索敵範囲に `* 0` を掛けており、**効果が完全に無効化されていた**（プレースボ状態）。 | ロックオンパネルの有効距離（`senseRangeFor()`）をこのアップグレードで拡大するようにし、加えて画面外にいる強大な敵（脅威）を画面端の矢印と距離表示で警戒表示する新機能（`drawThreatWarning`）を実装した。敵AI自体の索敵範囲（プレイヤーを追う/逃げる判定）は変更せず、あくまでプレイヤー側の「察知・警戒」情報として実装した。 |
| `ramspeed` | 加速衝突 | 「高速移動中は〜」という表現だが、実際は現在の移動速度比（0〜1）に連続的に比例するだけで、明確な「高速移動状態」を示す見た目のフィードバックが無く体感しづらかった（ユーザー指摘のとおり）。 | 移動速度が最大速度の60%を超えると自機後方に加速光（グロー）が灯る視覚効果を追加し、説明文を「移動速度が最大速度に近いほど〜。自機に加速光が灯る」に更新して実挙動と一致させた。 |
| `lava` | 溶岩惑星 | 説明文は「与えたダメージの%を質量変換」だが、実装は即吸収（オーバーキル）時のみに限定された特殊処理だった。 | `damageEnemy()` 内に一般化し、接触・波動・衛星などあらゆるダメージ源で一律に効くようにした（説明文どおり）。 |
| `gwave` | 重力波 | 説明文は「周囲の敵と破片を引き寄せる」だが、実装は破片の吸引範囲拡大のみで、敵への重力には一切効いていなかった。 | プレイヤー重力（`applyPlayerGravity`）にも `gwave` のボーナスを適用し、敵にも実際に効くようにした。 |
| `flare` | 太陽フレア | 説明文は「扇状の炎」だが、実装は全方位に均等にダメージが飛ぶ `pulseDamage`（円形）だった。 | 進行方向を中心とした扇形の `coneDamage`（半角約60°）に変更し、視覚的なパーティクルも追加した。 |
| `binary` | 伴星 | 説明文は「ダメージと引力」だが、引力の実装が存在しなかった。 | 伴星の周囲に弱い敵を引き寄せる引力を追加した。 |
| `rings` | 惑星環 | 説明文「環の破片が触れた敵に追加ダメージ」は、実際には環専用の当たり判定ではなく通常の接触ダメージへの一律ボーナスだったため、表現をやや誇張気味だった。 | 実挙動に合わせ「衝撃を増幅し、接触時の与ダメージ+%」という説明文に修正した。 |

残りのアップグレード（惑星環の基礎効果・希少鉱脈・重力場強化・硬質地殻・衛星・磁場収束・
オーロラ帯・推進機関・地殻再生・密度増加・彗星の尾・隕石シールド・質量転換効率・磁気嵐・
コロナ質量放出・不死の芯）は、説明文と実装を突き合わせた結果、既に一致していることを確認した
（変更なし）。

### 3. 実プレイでの調整ループ（Playwright + Chromium）

`/opt/pw-browsers/chromium` を使い、実際に序盤→中盤→終盤→クリアまで自動プレイして計測した。
ヘッドレス環境では `requestAnimationFrame` が著しくスロットルされ実時間で計測すると非効率
だったため、開発時のみ一時的なデバッグフック（rAFに依存せずゲームロジックを同期的に多数
フレーム進める `forceTicks`、進化段階ごとの敵数・質量比分布・画面占有率を集計する `getStats`）を
`game.js` に追加して計測に使用し、**調整完了後にコミット前へ完全に削除した**（現在のコードには
含まれていない）。

調整ループは以下の3周を実施：

1. **1周目**: サイズ分布・質量上限（4→2倍）・合体クールダウンを実装して計測 → 敵の質量比分布は
   改善したが、終盤（巨大ガス惑星以降）で敵の質量比が0に近づき、脅威が全く出現しなくなる
   問題を発見（`enemyScaleMass` を生の質量のままEMA平滑化していたため、指数的に成長する
   終盤の質量に対して追従が全く追いつかなくなっていた）。
2. **2周目**: `enemyScaleMass` の平滑化を対数（log）空間に変更（質量の成長率が一定なら
   比率が収束する性質を利用）。さらに、敵の表示半径が `massToRadius`（質量の単純な立方根）
   のままだったため終盤の質量域で異常値になっていた根本原因を発見し、
   `enemyVisualRadius`（プレイヤーと同じSTAGESベースの補間）に置き換え。画面占有率は
   大幅に改善したが、計測（バッチ末尾の1点サンプリング）では依然「脅威0%」と出ており、
   一瞬だけ出現する脅威をサンプリングが取りこぼしている疑いがあった。
3. **3周目**: 計測ロジックをバッチ内の全ティックを走査する方式に変更し、脅威の遠方スポーン
   バイアス（`farBias`）を調整（0.78→0.68）。再計測の結果、目標分布どおり
   （餌74〜100%・拮抗0〜15%・脅威0〜15%、同時脅威数は最大2〜3体）に収まっていることを確認し、
   最終値として確定した。

## 実機フィードバック対応（第3回：質感・背景・ペーシング・エンドレスモード・獲物の周回軌道・数値表示バグ）

実機（スマートフォン）でのスクリーンショット2枚（巨星 Lv14、巨大ガス惑星 Lv10）による
プレイフィードバックへの対応。原因分析と対応は以下の通り。

### 1. 「赤い丸が安っぽい・すぐ消滅する」の正体

**正体の特定**: スクリーンショットに写っていた「のっぺりした赤い円の集団」「オレンジ/水色の
単色円」は、いずれも**破片**（`makeFragment`/`spawnFragments`、敵撃破や敵同士の合体で生成される
吸収可能な質量粒）だった。以前の `Renderer.drawFragment` は単色 `fillStyle` のベタ塗り円＋
光源方向に白いハイライトを1点置くだけの実装で、他の天体（テクスチャ＋単一光源シェーディング）
とは全く違う質感になっていた。赤い集団に見えたのは、`hostile`（敵対天体、パレット基調色が
赤系 `#d1495f`）が撃破・合体で破壊された際に一度に最大14個の破片を同じ場所に放出するためで、
それぞれが単色の赤い円として重なって描画されていた。

**「すぐ消滅する」の原因**: 破片の寿命（`life`）自体は22秒あり短すぎるわけではなかった。
真因は個体数上限による間引き処理（`pruneBodyCounts`）だった。敵同士の合体連鎖
（`updateEnemyMutualGravityAndCollisions`）が起きると、一瞬で大量の破片（合体1回につき最大14個）
が同じ場所に湧く。この直後に毎フレーム走る間引き処理が `maxFragments` の上限を超えた破片を
「プレイヤーから遠い順」に問答無用で切り詰めるため、生まれたばかりの破片ごと消されてしまい
「出現直後に消える」ように見えていた。

**対応**:
- 破片は敵撃破時のパレット（base/dark/light の3トーン）を保持するように変更し、
  `Renderer.drawFragment` を、ある程度大きい破片（半径4.5px超）はテクスチャ付きの近似天体
  （小惑星と同じクレーター質感、単一光源シェーディング）、極小の破片は光源方向にハイライトの
  ある陰影グラデーションの球として描画するように書き換えた。単色ベタ塗りの円は完全に廃止した。
- 破片に生成からの経過時間（`age`）を追加し、`BALANCE.fragmentSpawnGraceSeconds`（3秒）未満の
  「生まれたて」の破片は間引き対象から除外するようにした（`trimFragmentsTo`）。あわせて
  `maxFragments`（40→60）・`maxTotalBodies`（55→80）の上限自体も引き上げ、通常のプレイでは
  生まれたばかりの破片が間引かれることがないようにした。

### 2. 背景の市松模様の原因

**原因の特定**: 星雲レイヤー（`generateNebulaLayer`）がタイル状に敷き詰めて描画される
（`drawBackground`）一方で、そのタイル画像自体はトーラス状にシームレスではなかった。各星雲の
光暈（radial gradient）はタイル中央付近ほど明るくタイル端に近づくほど暗く途切れており、
同じタイルを敷き詰めるとタイル境界を挟んで明暗が周期的に変化し、大きな正方形のムラ
（市松模様）として見えていた。

**対応**: 各光暈をキャンバスの上下左右斜め計9箇所（自分自身＋8方向の隣接コピー）に描画する
ことで、タイル端をまたぐ光暈も反対側の端に連続してつながるようにした（トーラス状ラップ）。
これにより、どの倍率・位置でタイルを敷き詰めても境界に不連続な明暗の段差が生じなくなった。

### 3. 中性子星区間のペーシング再配分

`cosmic/tools/simulate-pacing.js` で計測したところ、中性子星に進化してからブラックホール
（クリア）に至るまでの区間は、以前の設定では通常モードでも短すぎ、かつ**加速モードでは
段階別倍率を無視した固定値 `massGainMultiplier=1.0` を使っていたため、通常モードに対して
終盤ほど不釣り合いに短くなる**（実機フィードバックの「中性子星になってすぐ終わった」は
加速モードでのプレイだったと推測される）ことが判明した。対応:
- `STAGES` の巨星・中性子星の必要質量をそれぞれ引き上げた（巨星: 750,000 → 1,000,000、
  中性子星: 3,200,000 → 4,200,000）。
- `NORMAL_STAGE_PACING_MULT` の該当2段階の倍率を調整し、中性子星区間だけで通常モード
  平均 約9.2分（目標8〜10分の範囲内）になるよう再配分した。
- 加速モードは、通常モードと全く同じ段階別倍率の「形」を保ったまま定数 `FAST_MODE_SPEEDUP`
  （12.7）を一律に掛けるだけにした。これにより各進化段階の所要時間の**比率**は通常モードと
  完全に一致したまま、絶対時間だけが短くなる。

```
$ node cosmic/tools/simulate-pacing.js
=== 通常モード（段階別倍率） ===
  平均クリア時間: 61.3 分
    …巨星: 42.54分  中性子星: 52.06分  ブラックホール: 61.29分
  >>> 中性子星区間（中性子星到達→クリア）= 9.23 分
=== 加速モード（お試し・通常モードと同じ比率で一律短縮） ===
  平均クリア時間: 5.4 分
  >>> 中性子星区間（中性子星到達→クリア）= 0.75 分
```

### 4. エンドレスモード（ブラックホール到達後も遊べる）

クリア後のリザルト画面に「そのまま遊ぶ（エンドレス）」ボタンを追加した（`triggerClear`/
`continueEndless`、`index.html` の `#btn-result-endless`）。選ぶと `player.endless = true` として
プレイを継続する。
- **脅威なし**: エンドレス中の敵スポーンは `BALANCE.endlessThreatChance`（既定0）に基づき、
  常に「非脅威（餌寄り）」個体としてロールし直す（`trySpawnEnemies`）。ブラックホールの質量は
  既に桁違いに大きいため、実質すべてを即座に飲み込める。
- **螺旋に落ちる演出**: 課題6で実装した「重力で引き寄せた天体の接線速度（角運動量）を減衰
  させる」仕組み（`applyPlayerGravity`）を、自機がブラックホール段階の間は**質量比に関わらず
  全ての天体**に適用するようにした。物理的な減衰そのもので実現しているため、近づいた天体は
  実際に螺旋を描きながら事象の地平線へ落ちていく。
- **質量は増え続け、HUDに総吸収数/質量を表示**: エンドレス中は左上に専用パネル
  （`#endless-hud`）を表示し、`player.absorbedCount`（総吸収数）と `player.mass`（現在の質量）を
  表示する。レベルアップ（アップグレード選択）は最終段階に到達した後もそのまま継続する
  （`checkLevelUp` の判定は進化段階と無関係に質量のみで行われるため、変更不要だった）。
- **オートセーブ・リロード後の継続**: 以前はクリア（ブラックホール到達）と同時に
  `clearSave()` でセーブを破棄していたが、これをやめてクリア後もセーブを継続するように変更
  （`player.endless` フラグも保存対象に追加、`save.js`）。「つづきから」でロードした際、
  ブラックホール到達済みなのに `endless` が false（＝まだ選択していない、クリア直後に
  リロードした等）の場合は、黙って継続せずもう一度リザルト画面を出して選択させる
  （`startGame`）。
- **任意のタイミングでリザルトに戻れる**: エンドレス中は一時停止メニューに「リザルトを見る」
  ボタン（`#btn-pause-result`）が表示され、現在の統計を反映したリザルト画面をいつでも開ける
  （「プレイに戻る」で再開）。

### 5. 岩石テクスチャの作り直し

**原因**: `generateAlbedoShapeTexture`/`generateEquirectTexture` の岩石質テクスチャは、低い
オクターブ（グリッドサイズ6が主成分）の値ノイズをそのまま `mixColor(dark, base, noise^1.6)` に
通していたため、数個の大きく滑らかな明暗の塊ができ、「白い斑点が数個貼り付いたサッカーボール」
に見えていた。

**対応**: `textures.js` に、大小さまざまな半径のクレーターを明示的に配置する
`getCraterField`/`craterShadeAt` を新設した。各クレーターは「縁が明るいリム」「底に向かって
暗くなるお椀」を持ち、多オクターブノイズによる岩肌の下地の上に重ねて陰影を計算する
（`isCrateredKind` が true のkind＝岩石片/小惑星/準惑星/彗星核のみに適用。惑星以降は変更なし）。
`u`（経度相当）はトーラス状に距離を測るため、球面図法・正距円筒図法のどちらでも継ぎ目が
出ない。あわせて `ENEMY_PALETTES.asteroid` を、白に寄らない彩度低めのグレー〜茶系5種類に
拡充した。プレイヤー序盤の「岩石片」「小惑星」もプレイヤーの描画が同じ `textures.js` の
関数を共有しているため、この修正が自動的に適用される。

### 6. 獲物が周回軌道に乗り続ける問題

**原因**: `applyPlayerGravity`（プレイヤーの重力が近傍天体に働く処理）は径方向の加速度だけを
加えており、真空中なので速度に摩擦を掛けていなかった。そのため、重力で引き寄せられた小天体が
たまたま横方向の初速（角運動量）を持っていると、エネルギーを失わずに安定した周回軌道に
乗ってしまい、いつまで経っても落ちてこない（＝吸収できない）ケースがあった。

**対応**: プレイヤーより十分小さく吸収可能な「明確な獲物」（質量比 `BALANCE.gravityPreyRatio`
＝0.68 未満）に限り、速度の接線成分（＝軌道角運動量に相当）を毎フレーム指数的に減衰させる
処理を追加した（動的摩擦・潮汐減衰の簡易近似、減衰レート `BALANCE.preyOrbitDampRate`＝2.4/秒。
半減期は1秒未満で、数秒以内に必ず螺旋を描いて落下する）。径方向の速度成分はそのまま保つ。
敵対的・拮抗〜格上の天体（脅威）はこの処理の対象外とし、従来どおりのスイングバイ挙動を
維持している。

### 追加調査: 「+32.59M」表示バグの原因

**原因の特定**: ダメージ・獲得数値の連続ヒットをまとめて表示する集計処理（`queueFloat`/
`flushFloatAggregates`）は、集計キーごとに0.35秒分の合計を1つの数値として表示する設計だった。
ところが、キル（敵撃破の直接質量獲得）・破片吸収・溶岩惑星（ダメージ変換）・捕獲した衛星の
破片吸収という**全く出所の異なる質量獲得**が、すべて同じキー `'player-gain'` に集計されて
いたため、画面のどこか離れた場所で起きた無関係な複数の獲得（例: 遠方で敵を1体撃破した直後に
近くで破片を何十個も連続吸収する等）が0.35秒の間にまとめて1つの巨大な数値として合算・表示
されていた。スクリーンショットの「+32.59M」（自機質量1.07Mの約30倍）は、実際の質量加算自体は
（`creditMass` 経由で）正しく行われていたものの、**表示上だけ**複数の無関係な獲得イベントが
1つの数値に集約されてしまった結果だった。

**対応**: 獲得の種類ごとに別の集計キー（`gain-kill`/`gain-fragment`/`gain-lava`/
`gain-satellite`）に分離した。同じ種類の連続ヒット（例: 破片を連続で何十個も吸収する）は
引き続きまとめて1つの数値として表示されスパムを防ぎつつ、種類の異なる獲得同士が混ざって
実態と乖離した数値になることはなくなった。

## 実機フィードバック対応（第4回：エンドレスモードの描画はみ出しバグ・敵サイズ・重力）

実機（スマートフォン）でのスクリーンショット1枚（エンドレスモード、ブラックホール Lv20、
質量2.29B）による、「画面左半分が巨大な青いガス惑星のテクスチャで覆われ、円形にクリップ
されずギザギザの四角い境界ではみ出して画面を覆う」という描画バグの報告への対応。

### 1. テクスチャが円からはみ出して画面を覆う描画バグ（最優先）

**再現**: Playwright + Chromium で、報告と同じ質量（2.29B、ブラックホール・エンドレス）の
セーブデータを直接 `localStorage` に注入して起動し、実機と同じ状況を再現した。数秒以内に
同様の「ギザギザの巨大な塊が画面を覆う」現象を確実に再現できた。

**根本原因の特定**: `ctx.drawImage()` の呼び出し引数（描画先の幅・高さ）と `ctx.arc()` の
半径を実行時にフックして記録したところ、原因は**敵ではなく破片（`makeFragment`）の表示半径**
だった。`radius: Math.max(2.2, massToRadius(mass) * 0.6)`（`massToRadius(mass) = 6 * mass^(1/3)`）
には一切の上限が無く、エンドレスモードで敵の質量上限（`enemyMassCapMult` ×
プレイヤー質量、数十億に達する）を超えた分がそのまま「あふれた質量」として破片の質量になる
（`updateEnemyMutualGravityAndCollisions` の `overflow`）。この結果、破片1個の質量が数億〜
数十億に達し、`massToRadius` がワールド半径で数千という桁外れの値を返していた。敵専用の
画面占有率クランプ（`screenRadiusCapFor`）は破片には適用されておらず、この巨大な破片が
画面を覆うほど拡大されて描画され、かつクリップ処理が一切無かったため、LODキャッシュ用
オフスクリーンキャンバス（`getNearBodyFrame`）の矩形領域そのままの輪郭（不規則形状＝
ジャガイモ型の破片テクスチャのジャギー含む）が画面いっぱいにはみ出して見えていた。

**対応**（要求どおり (a)(b) の両方を実施）:
- **(a) 円形クリップの徹底**: `Renderer.drawRotatingGlobe`／`Renderer.drawFragment` の
  テクスチャ描画（`drawImage`）の前に、必ず `ctx.save(); ctx.beginPath(); ctx.arc(...); ctx.clip();`
  で円形にクリップしてから描画し、`ctx.restore()` で確実に元に戻すようにした。クリップ半径は
  公称半径よりわずかに広い `sr * 1.45`（不規則形状の最大張り出し1.38倍・大気の縁光1.06倍を
  誤って切り取らないための余裕）。これにより、たとえ半径計算やテクスチャキャッシュが
  想定外の値になっても、描画結果が矩形にはみ出すことは構造的に無くなる。
- **(b) 表示半径の絶対上限**: 破片の表示半径そのものに小さな絶対上限
  `FRAGMENT_MAX_RADIUS`（22ワールド単位）を導入した（`entities.js`・`makeFragment`）。
  破片が持つ実際の `mass`（吸収時に得られる質量の報酬値）は変更せず、**見た目だけ**を
  頭打ちにしている。加えて、`game.js` の描画ループに画面短辺の42%を絶対上限とする
  `hardMaxSr` を追加し、敵・破片・プレイヤー・捕獲した衛星すべての表示半径をこの値で
  クランプする二重の安全弁を設けた。
- テクスチャキャッシュ（`_albedoCache`／`_equiCache`／`_atmoCache`）が無制限に増え続けて
  いた点も、他のLODキャッシュと同様に上限件数を設けて古いものから破棄するようにし、
  長時間プレイでのメモリ使用量増大（実機での不安定要因になり得る）を抑えた。

**検証**: 質量 2.29B（報告と同条件）・50B・990B の3水準で、それぞれ15〜20秒間の
エンドレスプレイをPlaywrightで再現し、`ctx.arc`/`ctx.drawImage` の呼び出し引数を監視。
修正前は数フレームおきに半径580px相当（クリップ safety netの上限に張り付く＝実際の
破片半径はさらに大きい）の描画が発生していたが、修正後は全ケースで異常な大きさの
描画呼び出しが消え、破片の最大表示半径は常に22（`FRAGMENT_MAX_RADIUS`）に収まることを
確認した。スクリーンショットでも、ブラックホール（小さく円形にレンダリングされる）と
周囲の小さな破片・敵のみが表示され、画面を覆うテクスチャのはみ出しは再発しなかった。

### 2. エンドレスモードで敵がデカすぎる問題

**原因**: 敵の表示半径 `enemyVisualRadius(mass)` は `STAGES.radiusBase` を使った補間だが、
質量がブラックホールの閾値（1300万）を超えると `stageIndexForMass` が最終段（ブラック
ホール）で頭打ちになり、それ以上どれだけ質量が増えても**常に同じ半径**（プレイヤーの
最大表示半径と同一）を返し続けていた。エンドレスモードではプレイヤー・敵の両方の質量が
この閾値をはるかに超えて成長するため、敵が常にプレイヤーと同じ大きさに見えてしまい、
「ブラックホールがすべてを呑む爽快感」を損なっていた。

**対応**: `enemyVisualRadius(mass, player)` に `player` を渡せるようにし、エンドレス中かつ
質量が最終段で飽和している場合に限り、プレイヤーとの質量比の**立方根**でなめらかに縮小した
上で、上限をプレイヤー表示半径の**0.5倍**に固定するようにした（`entities.js`）。
`makeEnemyBody`・敵同士の合体成長（`updateEnemyMutualGravityAndCollisions`）の両方の
半径計算経路に反映した。

**検証**: 質量2.29B〜990Bのエンドレスプレイを複数回実施し、毎回、生存中の敵の最大表示
半径とプレイヤー表示半径の比を記録したところ、常に0.41〜0.46倍（要求の「半分以下」を
満たす）に収まることを確認した。通常モード終盤（中性子星〜巨星）についても同様の
飽和が起きないか確認したが、この区間では質量がまだ最終段の閾値に達していないため
半径は正常にステージ内補間され、既存のバランス（明確に大きい「脅威」個体はプレイヤーの
2〜3倍程度まで意図的に大きく見せている）に問題は見られなかった。通常モードで最終段
（ブラックホール）に到達した直後はクリア画面に遷移してプレイが止まるため（エンドレスを
選ぶまで質量が伸び続けることはない）、この経路での同様の破綻は発生しない。

### 3. 重力が強すぎる問題

**原因（実測シミュレーションで確認）**: プレイヤー重力の強さ `GRAV_CONST * player.mass` は
質量に比例して際限なく大きくなる一方、その結果生じる加速度は上限 `GRAV_MAX_ACCEL` で
一律にクランプされる設計だった。プレイヤー質量が終盤・エンドレスで数十億に達すると、
有効射程 `GRAV_PLAYER_RANGE` 内のほぼ全域で瞬時にこの上限まで加速度が張り付き、
「射程に入った瞬間、画面半分先からでも一瞬で吹き飛ぶように突っ込んでくる」挙動になって
いた（射程を狭めるだけでは、範囲内での加速度の激しさ自体は変わらないことをシミュレーション
で確認した）。

**対応**: `entities.js`／`data.js` の重力関連定数を全体的に見直した。
- `GRAV_CONST`: 46 → 30、`GRAV_PLAYER_RANGE`（有効射程）: 1400 → 350（画面半分よりも
  十分近い距離でのみ働くようにした）、`GRAV_MAX_ACCEL`（加速度上限）: 900 → 140、
  `BALANCE.preyGravityBoost`: 5.0 → 2.2 に引き下げた。
- 敵同士の相互重力（`ENEMY_GRAV_CONST`: 5.2→3.0、`ENEMY_GRAV_RANGE`: 260→190、
  相互引力の加速度上限: 260→160）も同様に弱め、敵対的な軌道の乱れを穏やかにした。
- 序盤の螺旋落下吸収（接線速度の指数減衰 `preyOrbitDampRate` と径方向ブースト）の
  仕組み自体は変更していない。

**検証**: 実際のゲームループ内に獲物を配置してPlaywrightで追跡した。
  - 序盤（プレイヤー質量300相当）: 120ワールド単位先に静止した獲物が、既存どおり
    緩やかに軌道を落としながら4〜5秒程度で吸収される（螺旋落下吸収は維持）。
  - エンドレス（質量2.29B）: 画面半分相当（555ワールド単位）に置いた獲物は新しい
    有効射程（350）の外のため引力の影響を受けず、遠方から一瞬で吹き飛んでくることは
    無くなった。画面の4割弱相当（220ワールド単位）まで近づいた獲物は、0.7秒ほどで
    滑らかに加速しながら吸収され、「近づいたものがすっと吸われる」体感になることを
    確認した。

## 実機フィードバック対応（第5回：彗星の狙い撃ち・破片の消滅）

実機フィードバック4点（彗星の突撃・環の見た目・破片の消滅・天体の矩形欠け）のうち、
描画層は今後 WebGL(Three.js) による本格3D化へ全面移行する方針となったため、環の3D化と
矩形欠けの描画修正は打ち切り、3D化後も引き続き有効なゲームプレイ側の2点のみ対応した。

### 1. 彗星がプレイヤーに突撃し、食われて勝手にレベルアップしてしまう問題

**原因の特定**: `trySpawnEnemies`（`game.js`）の彗星スポーンは、プレイヤー位置から
`spawnR*(0.15〜0.65)` の範囲内の点を明示的に狙って直線的に突っ込む「狙い撃ち」軌道
だった。さらに `pickEnemyKind` の確率しきい値の組み方に誤りがあり、`hostile` の抽選が
`stageIdx>=1` でしか行われないため、序盤（`stageIdx===0`）は本来 hostile 用に予約される
はずの確率区間もそのまま彗星判定に落ちてしまい、**序盤ほど彗星の出現率が高くなる**
逆転現象が起きていた（意図: 全ステージ16%、実際の序盤: 26%）。

**対応**:
- `pickEnemyKind` を累積しきい値方式に書き直し、序盤（`stageIdx<=1`）は彗星の出現確率
  自体を 16% → 6% に引き下げた。
- 彗星の進行方向をプレイヤー位置と完全に無関係な**ランダム方向**にし、プレイヤーとの
  最接近距離（垂直オフセット）も `spawnR` の 0.25〜1.1倍を基本とする広い範囲からランダムに
  選ぶようにした（＝視界をランダムな方向・オフセットで横切る軌道）。12%の確率でのみ
  0〜0.25倍の「近め」の通過を許し、直撃コースになるのはさらに稀（近め抽選かつオフセットが
  たまたま非常に小さい場合のみ）にとどめた。
- 序盤（`stageIdx<=1`）は彗星1体あたりの質量も追加で縮小（`stageIdx===0`は0.35倍、
  `stageIdx===1`は0.6倍）し、序盤に受動的に大量質量を得てレベルアップしてしまうことを防いだ。

**検証**（Playwright、加速モードで序盤を自動観測）: 出現した彗星の進行方向とプレイヤー方向の
内積（1=完全な狙い撃ち）を継続サンプリングしたところ、平均は0.13〜0.16程度（ランダム方向なら
理論上0付近）で、明確な狙い撃ちは解消された。序盤の彗星の質量も1桁小さい値（例: 質量0.16〜0.20、
基準質量1.0前後の場面）で生成されることを確認した。

### 2. 破片が自機の近くで消えてしまう問題

**原因の特定**: `updateFragments`（`game.js`）は破片ごとに毎フレーム `life -= dt`（寿命22秒）
していたが、これはプレイヤーに引き寄せられて接近している最中・目前まで来ている最中でも
無条件に進み、「吸収判定（`d < playerRadius*0.9`）に届く直前で寿命切れになり、何の見返りも
なく消滅する」ケースが起きていた。プレイヤーの近くほど発生しやすいため「目の前で拾おうと
した欠片がふっと消える」という体感の直接の原因だった（個体数上限による間引き
`pruneBodyCounts`／`trimFragmentsTo` は元々プレイヤーから遠いものを優先して間引く設計で
あり、こちらは原因ではなかった）。

**対応**: 画面内＋αの「安全半径」（`fragmentSafeRadiusFor()` = 画面対角線の0.65倍 ÷ カメラ
ズーム）を導入し、プレイヤーとの距離がこの半径未満の破片は寿命を消費しない（`life`を減らさない）
ようにした。寿命切れで消滅するのは安全半径の外（画面にほぼ映らない・触れられない遠方）に
いる破片だけに限定される。個体数上限による間引きは従来どおり遠方優先のため、近傍の破片は
二重に保護される。

**検証**（Playwright）:
- 重力吸引レンジの外・安全半径の内側（プレイヤーから300ワールド単位）へ寿命22秒の破片を
  3個生成し、25秒（寿命を超える時間）待って生存を確認したところ、3個とも消滅せず、`life`
  も22.00のまま（＝寿命が消費されていない）ことを確認した。
- 通常プレイでも、安全半径内の破片数が敵の合体連鎖による増加・プレイヤーの吸収による減少
  以外の理由で不自然に急減する挙動は見られなかった。

### 検証環境・確認事項

Playwright + Chromium（`/opt/pw-browsers/chromium-1194`）でローカルHTTPサーバー越しに実プレイし、
上記の彗星軌道・破片生存に加えて、コンソールエラーが一切発生しないこと（`pageerror`/
`console.error` を監視、0件）を確認した。検証・計測に使ったデバッグフック（`window.__debugState`
等）はテスト専用スクリプト側にのみ存在し、コミットする `game.js` 本体には一切含めていない。
`node --check` で全JSファイルの構文を確認済み。セーブデータの構造（`save.js`）は変更していない
ため `SAVE_KEY`（`cosmic-eater-save-v4`）はそのままで、既存セーブとの互換性に影響はない。

## 対応環境

依存ライブラリなしの静的 HTML5 + Canvas 2D。PC（マウス）・スマートフォン（タッチ）の両方に対応しています。
